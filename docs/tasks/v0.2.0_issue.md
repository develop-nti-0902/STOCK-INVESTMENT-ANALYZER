  ## 概要
  銘柄マスタの初期データ投入は手動CSVに頼るのではなく、サービス層でJPX等の公式データソースから取得し、Repository経由でDBへ格納するパイプラインを実装します。


  ## 詳細

  ### 参照仕様書
  - `docs/architecture/architecture_overview.md`
  - `docs/architecture/layers/service_layer.md`
  - `docs/architecture/layers/data_access_layer.md`
  - `docs/architecture/layers/data_storage_layer.md`

  ### 実装内容

  #### 1. データ取得（サービス層）
  - JPX（日本取引所グループ）や公開APIから銘柄一覧を定期取得するフェッチャーを実装します。アーキテクチャ仕様に合わせ、サービス名・責務・ファイル配置は以下の通りに整合します:
    - サービス層（ドメイン配置）: `StockMasterService`（実装ファイル例: `app/services/market_data/stock_master/service.py`）
    - フェッチャー（core基盤/ドメイン）: `StockMasterFetcher`（実装例: `app/services/market_data/stock_master/fetcher.py` または `app/services/core/fetchers/jpx_fetcher.py`）
    - セーバー/アップデータ: `StockMasterSaver` / `StockMasterUpdater`（`app/services/market_data/stock_master/saver.py`, `updater.py`）
  - フェッチャーはデータ取得 -> 正規化 -> バリデーション の責務を持ち、CSVやHTML、APIいずれのソースにも対応できる形にします（共通基盤: `app/services/core/fetchers/`）。

  #### 2. サービスロジック（サービス層）
  - `app/services/stock_master_service.py` を実装し、フェッチャーから得た銘柄データをRepositoryに渡して永続化します。
  - サービスはバルク処理、UPSERTポリシー、エラーハンドリング、リトライ、ログ出力を担当します。


  #### 3. Repository実装と連携
  - アーキテクチャ仕様に合わせて、Repository名と配置は以下を推奨します:
    - マスタ系: `MasterRepository` 実装ファイル `app/repositories/master.py`
    - 株価データ系: `StockRepository` 実装ファイル `app/repositories/stock.py`
  - `MasterRepository` に `bulk_create()`/`upsert()` を実装し、サービスはRepositoryの公開メソッドのみを使用します。トランザクション管理は共通モジュール(`app/utils/database.py`)の `get_db()` によるライフサイクルに従います。

  #### 4. 初期投入コマンド/スクリプト（運用用ラッパー）
  - `scripts/databaseSetup/seed_via_service.py`（新規）を用意し、開発環境で手動実行できるようにします。
  - このスクリプトは内部でサービスを呼び出し、フェッチ->保存のワークフローを実行します。
  - 既存の `scripts/databaseSetup/seed_data.py` はオプション的に残す（ローカル検証用）ものの、ドキュメントで推奨しない旨を明記します。

## 概要
既存の `scripts/databaseSetup` 配下で行っているテーブル作成・セットアップ処理を Alembic 管理へ移行します。これによりスキーマの履歴管理、チーム間共有、CI 上での安定した適用が可能になります。

## 目的
- マイグレーション履歴の管理と再現性の確保
- CI でのマイグレーション適用テストを実装
- ローカル/CI のスキーマ初期化手順を統一

## 実施方針（要点）
- 既存 SQL とスクリプトを調査して現状スキーマを把握する
- Alembic を初期化して `alembic/env.py` を非同期エンジン + `target_metadata = Base.metadata` に対応させる
- 自動生成で問題がなければ `--autogenerate`、差分が大きければ手動マイグレーションを作成する
- `scripts/databaseSetup` のエントリは `alembic upgrade head` を呼ぶように置換する
- CI ワークフローに `alembic upgrade head` の検証ステップを追加する

## 手順（詳細）
1. 既存スクリプト調査
  - `scripts/databaseSetup/sql/` の SQL ファイルを一覧化し、テーブル/インデックス/制約の依存順を把握する
  - `setup_db.bat` / `setup_db.sh` の実行フローを明確化する

2. Alembic 初期化と設定
  - `alembic init alembic` で初期構成を作成
  - `alembic.ini` を環境変数ベースで DB URL を読み取るように調整
  - ファイルエンコーディングを UTF-8 に設定

3. `alembic/env.py` のカスタマイズ
  - 非同期エンジン（`create_async_engine`）と `asyncio` 対応の記述を追加（Alembic Async cookbook 準拠）
  - `app.models` の `Base.metadata` を `target_metadata` に設定
  - 自動差分 (`--autogenerate`) が正しく動作するようモデル読み込みの副作用を抑制する

4. 初期マイグレーション作成
  - 自動生成で問題なければ `alembic revision --autogenerate -m "Initial database schema"`
  - PostgreSQL 固有拡張や特殊インデックスは `op.execute()` を使って手動で追加
  - 生成マイグレーションは `alembic/versions/` に格納

5. スクリプト差替え・ラッパー作成
  - `scripts/databaseSetup/setup_db.bat` / `setup_db.sh` を `alembic upgrade head` を呼ぶ実装に更新
  - 開発向けラッパー（`migrate.bat` / `migrate.sh`）を用意して使い方を明文化

6. CI 統合
  - `.github/workflows/ci.yml` に Postgres 起動 → `alembic upgrade head` → テスト のステップを追加

7. ドキュメント更新
  - `scripts/databaseSetup/README.md` を新規作成し、移行手順・ローカル実行手順・トラブルシューティングを記載

## 受け入れ条件
- `alembic/` ディレクトリと初期設定ファイルがリポジトリに存在する
- `alembic/env.py` が非同期エンジンと `target_metadata = Base.metadata` に対応している
- 初期マイグレーション（`alembic/versions/*.py`）が作成され、既存 SQL と同等のスキーマを作成する
- `scripts/databaseSetup/setup_db.bat` / `setup_db.sh` が `alembic upgrade head` を利用するよう更新されている
- `alembic upgrade head` でテーブルが作成され、`alembic downgrade base` で削除できることを確認済みである
- CI ワークフローでマイグレーション適用が成功する

## ティアダウン（teardown）
- 初期マイグレーションの `downgrade()` を正確に実装する（外部キーは逆順で DROP）
- `scripts/databaseSetup/teardown.sh` / `teardown.bat` を用意し、デフォルトで `alembic -c alembic.ini downgrade base` を実行できるようにする
- CI ではデータ破壊を避けるため、コンテナ破棄（`docker compose down -v`）や専用テスト DB を推奨する

## 技術的考慮事項
- `--autogenerate` はモデルと SQL の整合が取れているときに有効。差分が大きい場合は手動記述を優先
- PostgreSQL 特有の機能（部分インデックス、拡張モジュール等）は `op.execute()` で対応する
- `app` 側のモデルインポートで副作用が発生しないよう注意（遅延インポート等を検討）

## 概要
v0.1.0で定義した抽象インターフェースを実装し、具体的なRepository基底クラスを作成します。

## 詳細

### 実装内容

#### 1. Repository基底クラス実装 (`app/repositories/base.py`)
以下のメソッドを実装:
- `__init__(session)`: セッション受け取り
- `async get(id) -> Optional[Model]`: IDで単一取得
- `async get_multi(skip=0, limit=100) -> List[Model]`: ページネーション付き複数取得
- `async create(data: dict) -> Model`: 新規作成
- `async update(id, data: dict) -> Optional[Model]`: 更新
- `async delete(id) -> bool`: 削除
- `async count() -> int`: 件数取得
- `async exists(id) -> bool`: 存在確認

共通機能:
- トランザクション管理（自動コミット/ロールバック）
- エラーハンドリング
- ロギング
- Generic型による型安全性

#### 2. StockMasterRepository実装 (`app/repositories/stock_master_repository.py`)
`BaseRepository` を継承し、銘柄マスタ固有の操作を追加:
- `async get_by_symbol(symbol: str) -> Optional[StockMaster]`: 銘柄コードで取得
- `async get_by_market(market: str) -> List[StockMaster]`: 市場別取得
- `async search(query: str) -> List[StockMaster]`: 部分一致検索
- `async bulk_create(data_list: List[dict]) -> List[StockMaster]`: 一括作成
- `async upsert(data: dict) -> StockMaster`: UPSERT処理

#### 3. BatchExecutionRepository実装 (`app/repositories/batch_execution_repository.py`)
バッチ実行履歴の操作:
- `async create_job(job_type: str) -> BatchExecution`: ジョブ作成
- `async update_status(id, status: str)`: ステータス更新
- `async mark_completed(id, success_count, failed_count)`: 完了マーク
- `async get_by_job_type(job_type: str) -> List[BatchExecution]`: ジョブ種別で取得
- `async get_recent(limit: int) -> List[BatchExecution]`: 最近の実行履歴

#### 4. 依存性注入の実装
- `app/dependencies.py` にRepository取得関数追加
- FastAPIの依存性注入で使用
- 例:
  ```python
  def get_stock_master_repository(
      session: AsyncSession = Depends(get_db)
  ) -> StockMasterRepository:
      return StockMasterRepository(session)
  ```
