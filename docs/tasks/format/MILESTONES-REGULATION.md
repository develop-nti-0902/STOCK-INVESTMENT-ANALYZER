## 1. 概要
本ドキュメントは、リポジトリ内でのMilestone作成規約を定めます。プロジェクトの進捗管理とリリース計画を明確にし、チーム全体で目標を共有することを目的とします。

## 2. Milestoneタイトルのフォーマット
Milestoneタイトルは必ず日本語で記載し、下記のいずれかのフォーマットに従ってください。

### バージョンリリース型
```
v<major>.<minor>.<patch> - <リリース名>
```

### フェーズ型
```
Phase <番号>: <フェーズ名>
```

- `v<major>.<minor>.<patch>`: セマンティックバージョニングに従ったバージョン番号
- `<リリース名>`: そのバージョンの主要な特徴や目標を表す名前（任意）
- `Phase <番号>`: プロジェクトのフェーズ番号
- `<フェーズ名>`: フェーズの内容を表す名前

## 3. バージョン命名規則
セマンティックバージョニング（Semantic Versioning 2.0.0）に準拠します。

- **Major（メジャー）**: 互換性のない大きな変更
- **Minor（マイナー）**: 後方互換性のある機能追加
- **Patch（パッチ）**: 後方互換性のあるバグ修正

例: `v1.0.0`, `v1.2.0`, `v1.2.1`

## 4. Milestone説明文のテンプレート
Milestone説明文は以下の構造で記載してください。

```markdown
## 目標
<!-- このマイルストーンで達成する主な目標 -->

## リリース予定日
<!-- YYYY-MM-DD形式で記載 -->

## 主要機能・変更
<!-- このマイルストーンに含まれる主要な機能や変更 -->
- 機能1
- 機能2
- 機能3

## 対象Issue
<!-- 含めるべきIssueの概要や条件 -->
- [ ] #xxx: Issue概要1
- [ ] #xxx: Issue概要2

## リリースノート
<!-- リリース時に公開する情報（リリース後に更新） -->

## 備考
<!-- その他の注意点や依存関係 -->
```

## 5. ルール（必須）
- タイトルは**日本語**で記述すること（バージョン番号を除く）。
- バージョンリリース型の場合、セマンティックバージョニングに従うこと。
- 「目標」「リリース予定日」「主要機能・変更」は必須項目とし、省略しないこと。
- リリース予定日は `YYYY-MM-DD` 形式で記載すること。
- Milestoneには明確な完了条件（全Issueのクローズなど）を設定すること。
- Milestone作成時にはDue Date（期限）を設定すること。
- 進捗状況を定期的に確認し、必要に応じて調整すること。

## 6. 例

### 例1: メジャーバージョンリリース

**タイトル:**
```
v1.0.0 - 初回リリース
```

**説明文:**
```markdown
## 目標
株価投資分析システムの初回リリース。基本的な株価データ取得・保存・表示機能を提供する。

## リリース予定日
2025-12-31

## 主要機能・変更
- 株価データ取得APIの実装
- データベース設計と実装
- 銘柄一覧表示機能
- 株価チャート表示機能
- 基本的な分析機能

## 対象Issue
- [ ] #1: データベース設計
- [ ] #5: 株価データ取得API実装
- [ ] #10: フロントエンド基本構造実装
- [ ] #15: 銘柄一覧画面実装
- [ ] #20: チャート表示機能実装

## リリースノート
（リリース時に更新）

## 備考
- 本番環境へのデプロイ手順を事前に確認
- セキュリティレビューを実施
- パフォーマンステストを完了させること
```

### 例2: マイナーバージョンリリース

**タイトル:**
```
v1.1.0 - ポートフォリオ管理機能追加
```

**説明文:**
```markdown
## 目標
ユーザーが保有銘柄を管理できるポートフォリオ機能を追加する。

## リリース予定日
2026-02-28

## 主要機能・変更
- ポートフォリオ管理機能
- 保有銘柄の損益計算
- ポートフォリオ分析レポート
- CSV一括インポート機能

## 対象Issue
- [ ] #50: ポートフォリオデータモデル設計
- [ ] #51: ポートフォリオCRUD API実装
- [ ] #52: ポートフォリオ画面実装
- [ ] #53: 損益計算ロジック実装
- [ ] #54: CSVインポート機能実装

## リリースノート
（リリース時に更新）

## 備考
- v1.0.0の安定稼働を確認してから開始
- 既存データとの互換性を保つこと
```

### 例3: パッチバージョンリリース

**タイトル:**
```
v1.0.1 - バグ修正
```

**説明文:**
```markdown
## 目標
v1.0.0で報告された重大なバグを修正する。

## リリース予定日
2026-01-15

## 主要機能・変更
- 株価保存処理の重複INSERT修正
- チャート表示のメモリリーク修正
- 日付フィルタの不具合修正

## 対象Issue
- [ ] #210: 株価保存処理で重複INSERTが発生する
- [ ] #211: チャート表示でメモリリークが発生
- [ ] #212: 日付フィルタが正しく動作しない

## リリースノート
（リリース時に更新）

## 備考
- 緊急度が高いため優先的に対応
- ホットフィックスとして早急にデプロイ
```

### 例4: フェーズ単位のマイルストーン

**タイトル:**
```
Phase 1: プロジェクト基盤構築
```

**説明文:**
```markdown
## 目標
開発環境・CI/CD・基本的なプロジェクト構造を整備し、開発を開始できる状態にする。

## リリース予定日
2025-12-15

## 主要機能・変更
- 開発環境セットアップ
- CI/CDパイプライン構築
- プロジェクト構造定義
- コーディング規約策定
- テスト戦略策定

## 対象Issue
- [ ] #1: 開発環境構築ガイド作成
- [ ] #2: CI/CD設定
- [ ] #3: ディレクトリ構造定義
- [ ] #4: コーディング規約ドキュメント作成
- [ ] #5: テスト戦略ドキュメント作成

## リリースノート
N/A（内部マイルストーンのため）

## 備考
- 全開発者が環境構築を完了できること
- ドキュメントは随時更新
```

## 7. ベストプラクティス & 注意点
- Milestoneは明確なゴールと期限を持つべき。曖昧な目標は避ける。
- 1つのMilestoneに含めるIssueは適切な数に抑える（目安: 5-20個）。
- 大きすぎるMilestoneは複数に分割し、段階的にリリースする。
- リリース予定日は現実的な日程を設定し、バッファを持たせる。
- Milestone達成後は必ず振り返りを行い、次回に活かす。
- 進捗が遅れている場合は早めにスコープ調整や期限変更を検討する。
- クローズ後は必ずリリースノートを更新し、変更内容を記録する。
- 依存関係のあるMilestone同士は明確に管理し、順序を守る。
