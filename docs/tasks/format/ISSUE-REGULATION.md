## 1. 概要
本ドキュメントは、リポジトリ内でのIssue作成規約を定めます。チームでのタスク管理・追跡性を高め、コミットメッセージとの一貫性を保つことを目的とします。

## 2. Issueタイトルのフォーマット
Issueタイトルは必ず日本語で記載し、下記のテンプレートに従ってください。

```
[<type>](<scope>) <subject>
```

- `[<type>]`: 下記のType一覧のいずれかを使用します。
- `(<scope>)`（任意）: 変更の影響範囲（例: api, services, repo, ui など）。省略可。
- `<subject>`: タスクの要約（日本語、簡潔に、50文字以内が推奨）。

## 3. Type一覧
- `feat`: 新機能追加
- `fix`: バグ修正
- `docs`: ドキュメントの変更
- `style`: フォーマットや空白、セミコロンなどのスタイル変更（機能に影響しない）
- `refactor`: リファクタリング（機能変更を伴わない内部改善）
- `perf`: パフォーマンス改善
- `test`: テストの追加・修正
- `chore`: ビルド・CI・ツール設定などの雑務

## 4. Issue本文のテンプレート
Issue本文は以下の構造で記載してください。

```markdown
## 概要
<!-- このIssueで何を達成するのかを簡潔に記載 -->

## 背景・目的
<!-- なぜこのタスクが必要なのか、どのような課題を解決するのか -->

## 実装内容
<!-- 具体的に何を実装・修正・変更するのか -->
- [ ] タスク1
- [ ] タスク2
- [ ] タスク3

## 受け入れ条件
<!-- このIssueを完了とみなすための条件 -->
- [ ] 条件1
- [ ] 条件2

## 参考資料
<!-- 関連するドキュメント、Issue、PRなどへのリンク -->
- 関連Issue: #xxx
- 参考資料: [リンク]

## 補足事項
<!-- その他の注意点や備考 -->
```

## 5. ルール（必須）
- タイトルは**日本語**で記述すること。
- タイトルは必ず `[<type>] <subject>` または `[<type>](<scope>) <subject>` の形式にすること。
- タイトルは50文字以内を推奨し、句点（。）は付けない。
- Issue本文は必ずテンプレートに従って記載すること。
- 「概要」「背景・目的」「実装内容」は必須項目とし、省略しないこと。
- 「受け入れ条件」は完了判定のために明確に記載すること。
- 関連するIssueやPRがある場合は「参考資料」に記載すること。
- ラベルは適切に付与し、担当者・マイルストーンも設定すること。

## 6. 例

### 例1: 新機能追加

**タイトル:**
```
[feat](api) 銘柄一覧取得APIの実装
```

**本文:**
```markdown
## 概要
銘柄一覧を取得するためのAPIエンドポイントを実装する。

## 背景・目的
フロントエンドから銘柄情報を効率的に取得するため、REST APIエンドポイントが必要。

## 実装内容
- [ ] GET /api/stocks エンドポイント作成
- [ ] ペジネーション機能の実装（limit, offset）
- [ ] 検索パラメータ対応（銘柄コード、名前）
- [ ] レスポンススキーマの定義
- [ ] 単体テストの作成

## 受け入れ条件
- [ ] APIが正常に動作し、銘柄一覧が取得できる
- [ ] ペジネーションが正しく機能する
- [ ] テストカバレッジが80%以上
- [ ] APIドキュメントが更新されている

## 参考資料
- 設計資料: docs/api/stocks_api.md
- 関連Issue: #50

## 補足事項
将来的にはソート機能も追加予定だが、今回のスコープには含めない。
```

### 例2: バグ修正

**タイトル:**
```
[fix](services) 株価保存処理で重複INSERTが発生する
```

**本文:**
```markdown
## 概要
株価データ保存時に重複するレコードがINSERTされてしまうバグを修正する。

## 背景・目的
同一銘柄・日付の株価が複数回保存され、データの整合性が失われている。

## 実装内容
- [ ] UPSERT処理への変更
- [ ] 重複チェックロジックの追加
- [ ] 既存の重複データのクリーンアップスクリプト作成
- [ ] 再発防止のための統合テスト追加

## 受け入れ条件
- [ ] 重複INSERTが発生しない
- [ ] 既存データが正常にクリーンアップされている
- [ ] テストが追加され、全てパスする

## 参考資料
- バグ報告: #210
- 関連PR: #215

## 補足事項
本番環境でのデータクリーンアップは慎重に実施する必要がある。
```

### 例3: ドキュメント整備

**タイトル:**
```
[docs] API仕様書の更新
```

**本文:**
```markdown
## 概要
最新のAPI仕様に合わせてドキュメントを更新する。

## 背景・目的
実装とドキュメントが乖離しているため、開発者が混乱している。

## 実装内容
- [ ] エンドポイント一覧の更新
- [ ] リクエスト・レスポンス例の追加
- [ ] 認証方式の説明追記
- [ ] エラーコード一覧の整理

## 受け入れ条件
- [ ] 全エンドポイントのドキュメントが最新になっている
- [ ] サンプルコードが動作する
- [ ] レビューで承認を得る

## 参考資料
- 現在のドキュメント: docs/api/README.md

## 補足事項
なし
```

## 7. ベストプラクティス & 注意点
- タイトルは「何をするのか」を短く明確に書く。
- 「背景・目的」では「なぜこのタスクが必要なのか」を明記する。
- 「実装内容」はチェックリスト形式で具体的なタスクを列挙する。
- 「受け入れ条件」は完了判定のために明確で測定可能な基準を設定する。
- 大きなタスクは複数のIssueに分割し、親子関係や依存関係を明記する。
- Issue作成後はラベル・マイルストーン・担当者を適切に設定する。
- Issue番号はコミットメッセージやPRで参照し、トレーサビリティを確保する。
